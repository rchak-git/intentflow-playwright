INTENTFLOW FRAMEWORK ARCHITECTURAL CONTRACT:
1. UI Map Uniformity: Every entry in a UI map must be a Record<string, string>. The primary/root selector must ALWAYS be named 'main'. Optional fallback locators use 'alternate'. Complex widgets define sub-elements using descriptive keys (e.g., sourceSelect, addButton).
2. Polymorphic Control Architecture: All controls extend 'BaseControl'. The CommandDispatcher acts strictly as a router/orchestrator—it resolves the locator config and delegates execution to the appropriate control class based on widgetType.
3. Zod Schema Validation: All YAML steps must conform to the intentSchema.ts validation rules, including optional sub-actions (e.g., ADD, REMOVE) and dynamic values.
4. Resilience: BaseControl provides built-in action retry wrappers (default 2 retries) and locator retrieval methods (getPrimaryLocator, getAlternateLocator, getSubLocator).

Prioritized Backlog Roadmap
Here is the proposed, step-by-step roadmap for scaling IntentFlow to meet enterprise requirements:

Item 1: Dual ListBox Control Implementation
Goal: Create DualListBoxControl extending BaseControl.

Details: Support sub-actions (ADD, REMOVE, REMOVE_ALL) handling single or array values (string | string[]). Leverage named sub-locators (sourceList, targetList, addButton, removeButton) from UiMapEntry.

Item 2: Web Table / Grid Control Implementation
Goal: Create WebTableControl extending BaseControl.

Details: Support dynamic row/column matching (e.g., locate row where column "Course Name" equals "TypeScript Automation") and cell-level verifications or actions.

Item 3: Assertion Layer Standardization & Refinement
Goal: Refine verify intents across controls.

Details: Differentiate between DOM text (toHaveText) and form input values (toHaveValue). Add standard assertion types (TEXT_CONTAINS, VALUE_EQUALS, IS_ENABLED, IS_DISABLED).

Item 4: Runtime Context Store & Token Interpolation Engine
Goal: Enable dynamic data passing across execution steps.

Details: Introduce a runtime key-value context store (ContextStore). Enable variable generation (e.g., ${TIMESTAMP}) and value capture/interpolation (e.g., ${LK_UP[createdUserId]}) inside scenario steps.

Item 5: Custom Function Escape Hatch (F Flags & Handlers)
Goal: Execute non-standard custom JS/TS backend or UI logic.

Details: Implement a Custom Action Registry supporting CUSTOM_HANDLER and CUSTOM_SCRIPT intent types for edge-case test steps.
