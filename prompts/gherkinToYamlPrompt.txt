SECTION A: SUITE HEADER, NAMING & INTERPOLATION RULES
================================================================================
1. Header Metadata:
   - `page`: MUST be included if PAGE ROUTE URL is provided in Input Context (e.g., `page: "/user/profile"`). Omit ONLY if the suite relies purely on cross-suite handoffs.
   - `description`: High-level suite purpose description.
   - `uiMap`: MUST reference registered UI Map key or class (e.g., "MoodleLoginPageUiMap").
   - `includes`: MUST list all parent YAML suite files referenced in `preconditions:` (e.g., `includes: ["moodleLoginSteps.yaml", "moodleHomePageSteps.yaml"]`).

2. Strict Naming Contracts (Rule 2.6):
   - Public test execution targets inside `profiles:` MUST use the `td_` prefix (e.g., `td_successfulStudentLogin`, `td_navigateToMyCourses`).
   - Reusable interaction mechanics inside `sharedScenarios:` MUST use descriptive verb-first prefixes (`execute*` or `open*`, e.g., `executeOpenCourse`, `openUserMenuAndSelectOption`).

3. Token & Variable Interpolation Syntax (Rule 2.4):
   - Data properties MUST use `${data:variableName || 'default_value'}` fallback syntax or `${data:variableName}`.
   - NEVER use dot notation (`${data.var}`) or colon variations (`${data:var:default}`).
   - Dynamic extracted state MUST strictly use `${store:variableName}` notation.

4. Cross-Suite Preconditions Handoff (Rule 2.3 & 2.5):
   - When referencing a profile from an included parent YAML file inside preconditions, use dot-notation format: `refProfile: "parentSuiteSteps.td_profileName"`.

SECTION B: PATH 2 COMPOSITION & REUSABILITY LAWS
================================================================================
The YAML body MUST contain STRICTLY TWO top-level dictionary sections:
1. `sharedScenarios`: Dictionary object keyed by camelCase scenario names (prefixed with execute* or open*).
2. `profiles`: Named test execution targets (prefixed with td_*).

NEVER generate a 'tests:' block at the root level of the YAML file.

FOUR MANDATORY PATH 2 RULES:

1. Rule 2.2 — Domain-Driven Reusability & Parameterization:
   - Extract an interaction sequence into `sharedScenarios:` (prefixed with `execute*` or `open*`) whenever:
     a) It is referenced by two or more profiles in the suite, **OR**
     b) Even in a single-scenario prompt, the sequence represents a **reusable domain workflow or navigation/search action** that accepts parameterized inputs (e.g., `executeLogin`, `executeSearchAndOpenCourse`, `openUserMenuAndLogout`, `executeFilterAssignments`) likely to be reused by future test profiles with different datasets.
   - Keep steps inline inside `profiles:` ONLY when they are **test-specific verifications** or **one-off negative/edge assertions** unique to that single test case.
   - **Data Scoping:**
     - Steps inside `sharedScenarios:` MUST parameterize variable inputs using `${data:variableName || 'default_value'}` (or `${data:variableName}`).
     - Profiles (`td_*`) invoke the shared scenario via `refScenario:` and pass concrete literal values inside `data: { ... }`.
     - Any inline verification steps inside `profiles:` MUST use direct literal values (never `${data:...}`).

   ```yaml
   sharedScenarios:
     executeLoginSubmit:
       description: "Populates credentials and clicks login button"
       steps:
         - step: "Enter username into Username field"
           fieldKey: "moodle_login_usernameTextbox"
           intent: "populate"
           params:
             value: "${data:username || 'student'}"
