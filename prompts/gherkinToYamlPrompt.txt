SECTION A: SUITE HEADER, NAMING & INTERPOLATION RULES
================================================================================
1. Header Metadata:
   - `page`: MUST be included if PAGE ROUTE URL is provided in Input Context (e.g., `page: "/user/profile"`). Omit ONLY if the suite relies purely on cross-suite handoffs.
   - `description`: High-level suite purpose description.
   - `uiMap`: MUST reference registered UI Map key or class (e.g., "MoodleLoginPageUiMap").
   - `includes`: MUST list parent YAML suite files under `includes:` if a Parent RefProfile Key or Parent Suite File is provided (e.g., `includes: ["moodleHomePageSteps.yaml"]`).

2. Strict Naming Contracts (Rule 2.6):
   - Public test execution targets inside `profiles:` MUST use the `td_` prefix (e.g., `td_successfulStudentLogin`, `td_navigateToMyCourses`).
   - Reusable interaction mechanics inside `sharedScenarios:` MUST use descriptive verb-first prefixes (`execute*` or `open*`, e.g., `executeOpenCourse`, `openUserMenuAndSelectOption`).

3. Token & Variable Interpolation Syntax (Rule 2.4):
   - Data properties MUST use `${data:variableName || 'default_value'}` fallback syntax or `${data:variableName}`.
   - NEVER use dot notation (`${data.var}`) or colon variations (`${data:var:default}`).
   - Dynamic extracted state MUST strictly use `${store:variableName}` notation.

4. Cross-Suite Preconditions Handoff (Rule 2.3 & 2.5):
   - When referencing a profile from an included parent YAML file inside preconditions, use dot-notation format: `refProfile: "parentSuiteSteps.td_profileName"`.

SECTION B: PATH 2 COMPOSITION & REUSABILITY LAWS
================================================================================
The YAML body MUST contain STRICTLY TWO top-level dictionary sections:
1. `sharedScenarios`: Dictionary object keyed by camelCase scenario names (prefixed with execute* or open*).
2. `profiles`: Named test execution targets (prefixed with td_*).

NEVER generate a 'tests:' block at the root level of the YAML file.

THREE MANDATORY PATH 2 RULES:

1. Rule 2.2 — Reusability Threshold ($\ge 2$ Reference Rule):
   - Extract logic into `sharedScenarios:` ONLY if it is referenced by TWO OR MORE profiles ($\ge 2$).
   - If an interaction sequence is only referenced by a SINGLE profile, DO NOT create a sharedScenario! Keep `sharedScenarios: {}` empty and inline the steps directly inside that profile's `steps:` array.

2. Rule 2.1 — 1-Hop Redirection Limit:
   - A `sharedScenario` may reference another `sharedScenario` up to a maximum depth of ONE hop (`Scenario A -> Scenario B -> Steps`). Deeper nesting is strictly forbidden.

Rule  — Reusability Threshold (>= 2 Reference Rule):
   - Extract logic into `sharedScenarios:` ONLY if referenced by TWO OR MORE profiles (>= 2).
   - `sharedScenarios` MUST explicitly wrap steps inside a `steps:` array:

   ```yaml
   sharedScenarios:
     executeLoginSubmit:
       description: "Populates credentials and clicks login button"
       steps:
         - step: "Enter username into Username field"
           fieldKey: "moodle_login_usernameTextbox"
           intent: "populate"
           params:
             value: "${data:username || 'student'}"

3. Rule 2.3 & 2.5 — Shallow Preconditions & Explicit Setup Stacking:
   - Preconditions are resolved SHALLOWLY (1 level deep only). When a precondition profile executes, its inner preconditions are IGNORED.
   - Navigation profiles (e.g., `td_navigateToMyCourses`) MUST NOT hardcode login/authentication preconditions.
   - Test entry profiles requiring authentication or prerequisite page state MUST explicitly stack all preceding setup profiles in sequential order inside their top-level `preconditions:` array (e.g., `[moodleLoginSteps.td_successfulStudentLogin, moodleHomePageSteps.td_navigateToMyCourses]`).

CONTROL-TYPE CAPABILITY MATRIX & ALLOWED SUB-INTENTS:

A. CUSTOM_SELECT CONTROLS (widgetType: 'CUSTOM_SELECT'):

intent: "populate" --> params: { value: "${data:optionValue}" }

intent: "verify"   --> subIntent: ["contains", "equals", "state", "optionsContains"]

intent: "action"   --> subIntent: ["open", "close"]

B. WEB_TABLE CONTROLS (widgetType: 'WEB_TABLE' | 'TABLE'):

intent: "verify"  --> subIntent: ["cellText", "contains", "count", "rowCount", "allRowCheckboxesState"]

intent: "action"  --> subIntent: ["clickSubControl", "sortColumn"]

intent: "extract" --> subIntent: ["tableData"]

C. CARD / COMPOSITE CONTROLS (widgetType: 'CARD' | 'CONTAINER'):

intent: "action"  --> subIntent: ["clickSubControl", "click", "hover"]

intent: "verify"  --> subIntent: ["contains", "equals", "state"]

D. RADIO GROUP CONTROLS (widgetType: 'RADIO_GROUP'):

intent: "populate" --> params: { value: "${data:radioValue}" }

intent: "verify"   --> subIntent: ["contains", "equals", "optionsContains", "state"]

intent: "action"   --> subIntent: ["select"]

E. TEXTBOX / DROPDOWN / BUTTON / CHECKBOX / SEARCH / SELECT (Standard Elements):

intent: "action"   --> subIntent: ["click", "jsClick", "navigate", "pressKey"]

intent: "populate" --> params: { value: "${data:variableName}" }

intent: "verify"   --> subIntent: ["state", "contains", "urlContains"]

import { test } from '@playwright/test';
import { loadYamlSuite } from '../../../src/engine/yamlLoader';
import { CommandDispatcher } from '../../../src/engine/commandDispatcher';
import { SuiteSpec } from '../../../src/types/intentSchema';

const SUITE_PATH = 'tests/suites/<SuiteSubPath>/<pageName>Steps.yaml';

test.describe('<Feature Title> Workflows', () => {
  let suite: SuiteSpec;

  test.beforeAll(() => {
    suite = loadYamlSuite(SUITE_PATH);
  });

  test('<Scenario Description>', async ({ page }) => {
    const dispatcher = await CommandDispatcher.fromSuite(suite);
    await dispatcher.executeProfile(page, '<td_profileName>', suite);
  });
});
